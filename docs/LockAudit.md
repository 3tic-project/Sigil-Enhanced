# 锁与重入检查

从“添加 XHTML 副本后立即重命名”的文本缓存死锁继续检查自有 `src` 代码中的互斥锁、读写锁、Python GIL、条件等待、阻塞跨线程调用和持锁处理界面的路径。保留搜索栏在编辑器下方的布局。

锁修复提交为 `d6dec4d34`。后续 `bf991cc1a` 的生命周期检查见[空指针审查](NullPointerAudit.md)，最初反馈及 Windows 待测项目见[Windows E14 反馈修复](WindowsE14FeedbackFixes.md)。下方全量测试数字记录锁修复阶段的验证结果。

## 修复

| 路径 | 问题 | 处理 |
| --- | --- | --- |
| Python 错误报告 | 解释器互斥锁和 GIL 未释放就打开模态弹窗；弹窗中的再次调用会死锁，工作线程还可能创建界面 | 持锁时只提取 traceback；清理 Python 对象并释放两把锁后，将错误提示排到 GUI 线程下一轮事件处理。静默错误仍不弹窗 |
| Python 对象包装 | 构造和复制引用时未取得 GIL，跨线程复制可能丢失引用计数 | 所有引用计数修改均取得 GIL；替换时先保留新引用，再释放旧引用 |
| TOC 后台解析 | 持有书籍互斥锁等待资源读取，GUI 切换书籍也需要同一把锁 | 移除这把共享书籍锁，书籍切换和直接读取限于模型线程；异步刷新固定使用启动时的书籍引用。旧书籍在 GUI 收到完成通知后释放，避免工作线程销毁 QTextDocument。NCX 相对路径使用同一次读取保存的文件路径 |
| 目录标题选择窗口 | 整个模态窗口生命周期持有所有 XHTML 写锁；Agent 在 GUI 线程读取 nav 会卡死 | 移除窗口生命周期的锁；只在实际写入标题、层级、ID 时保护对应资源 |
| 标题连续编辑 | 首次修改标题会插入排版空白节点，后续修改层级和 ID 使用旧的节点位置，可能失效或写错位置 | 写入后更新同一资源各标题的节点位置，保留包含/隐藏等窗口状态；测试使用原始未排版的 XHTML 连续执行改名、改层级和 ID 写入 |
| OPF 版本警告 | 写锁内弹窗，回调读取包版本时尝试取得读锁；递归读写锁也不能切换锁模式 | 先记录已提示状态，再排队显示警告，避免写锁内启动事件循环 |
| 拼写检查 | 卸载词典后主/次词典缓存仍指向已经释放的 Hunspell 和编解码器；后台读取与重载互斥不完整 | 卸载同步清空缓存；共享词典、编解码器、语言映射和忽略词集合使用同一把锁，重载整体互斥。公开方法存在 `spell → load → addWord` 嵌套，因此这里使用递归互斥锁 |
| Agent 会话 | 监听器替换、ID 读取缺少同步；清空与创建新会话事件不是一个原子操作 | 使用既有会话锁保护状态。监听器调用和旧捕获对象销毁在锁外进行 |
| Agent 等待 | GUI 持续调用 `processEvents`，决定标志和栈上事件循环指针还存在跨线程未同步访问 | 使用正常事件循环等待、定时检查取消；循环指针受锁保护，跨线程排队退出循环。后台路径继续使用条件等待 |

没有把所有锁改为递归锁，也没有添加全局锁、请求门禁或持久化状态。前次文本缓存的递归锁修复继续保留。

## 其他检查

- `Resource` 重命名、移动和删除，以及 `FolderKeeper` 添加资源：资源通知位于相应临界区之外。
- `TempCleanup`：先获取待处理路径快照，再执行文件操作和 Python 释放回调；回调期间不持有队列互斥锁。释放回调在启动时配置，重试在 GUI 线程进行。
- XML 合法性检查、字体实体查询：临界区内只进行解析或实体查询，没有界面事件循环、阻塞 GUI 调用或用户回调。
- Agent 的书籍和翻译跨线程调用：同线程直接执行，其他线程才使用阻塞队列调用；调用入口没有持有上述会话或资源锁。继续由书籍所属线程执行界面和书籍操作。
- 批量搜索、更新引用、格式化等资源操作：检查读写临界区与等待、`processEvents` 的先后关系，并用现有集成测试覆盖复制、重命名、搜索、保存、插件和 Agent 操作。

这些检查不代表对所有调度顺序或 Qt、WebEngine、Python、Hunspell 内部锁的形式化证明。

## 回归测试

`lock_reentrancy_integration` 链接真实 Sigil 对象，使用独立设置目录和生成的 EPUB，包含九个独立进程场景：

1. Python 函数错误弹窗期间再次调用 Python。
2. Python 对象方法错误弹窗期间再次调用 Python。
3. 工作线程报告 Python 错误，GUI 弹窗期间再次调用 Python。
4. 多线程复制 Python 对象包装，核对引用计数与后续可用性。
5. 用信号量暂停真实 nav 读取，再切换书籍；确认排队刷新丢弃旧目录结果、旧书籍存活至读取完成且在 GUI 线程释放。
6. EPUB 2 NCX 嵌套目录、相对路径、片段与远程链接。
7. OPF 版本警告期间读取版本并再次修改，确认版本保持且只提示一次。
8. 卸载主词典后继续拼写检查；并发读取、建议、忽略词和多次强制重载。
9. 标题选择窗口打开期间读取 nav 与 XHTML 属性，在隐藏部分标题的情况下连续修改标题、层级并确认 ID 写入。

旧实现中，Python 函数弹窗、暂停目录读取后切换书籍、OPF 警告读回、标题窗口读目录均稳定触发进程超时；卸载词典后的快速拼写检查触发 `SIGSEGV`。

`agent_locking` 覆盖监听器重入、捕获对象析构重入、四线程追加/清空/读取/替换监听器、GUI 和工作线程确认、跨线程唤醒、取消及等待 CPU 用量；也加入轻量 Windows 检查工程和 CI。

另用 ThreadSanitizer 构建该测试检查会话与 GUI 等待路径。当前预编译 Qt 6.7.3 的 `QWaitCondition` 内部释放/重新取得互斥锁不在插桩范围内，完整 sanitizer 运行会报告 double-lock 和后续竞争；一个不含 Sigil 代码、只用 `QMutex`/`QWaitCondition` 的最小程序也复现相同报警。因此 sanitizer 运行使用 `--skip-qt-condition-wait`，只跳过工作线程的条件等待案例；普通 CTest 仍运行全部案例。没有添加 sanitizer 报警抑制，也不将这一路径记为 sanitizer 验证通过。

运行方式：

```sh
cmake --build cmake-build-debug --target Sigil agent_locking_test
ctest --test-dir cmake-build-debug -R '^(agent_locking|lock_reentrancy_integration)$' --output-on-failure
```

真实对象集成测试目前使用已有 macOS Ninja Debug 构建。Windows 检查工程可独立构建；Windows 10 的原生窗口、文件选择器和锁竞争仍需 Windows 实机复测。

## 锁修复阶段的验证结果（d6dec4d34）

- 应用及全部测试目标构建成功；锁专项九个真实对象场景、Agent 并发测试、目录编辑集成测试通过。Agent 并发测试还连续运行五次通过。
